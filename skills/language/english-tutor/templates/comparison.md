# 表達比較版型

適用於使用者比較兩個或多個英文單字、片語、句型、文法結構或完整表達，並希望理解它們在意思、句法、語氣、自然度或使用情境上的差異。

依比較對象與問題複雜度選用必要區段，不必逐項輸出。比較的目的不是只判斷「哪個對」，而是找出真正造成差異的因素。

## 1. 結論先行

先用簡潔繁體中文說明最重要的差異。

優先回答：

- 意思是否相同
- 文法是否都成立
- 句法結構是否不同
- 語氣或自然度是否不同
- 是否可以互換

若其中一個表達文法成立但意思不同，不可直接標示為「錯」。

例如：

`Send it as a POST request.`

與：

`Send it a POST request.`

兩句可以形成不同的合法句法結構，但 `it` 的角色不同，因此意思不同。

## 2. 結構對照

若差異涉及文法或句法，分別列出結構公式。

例如：

`Send it as a POST request.`

`send + O + as + NP`

與：

`Send it a POST request.`

`send + IO + DO`

必要時使用表格：

| 表達 | 結構 | 關鍵成分 | 角色 |
| --- | --- | --- | --- |
| Send it as a POST request. | `send + O + as + NP` | `it` | O：被傳送的內容 |
| Send it a POST request. | `send + IO + DO` | `it` | IO：接收者 |
|  |  | `a POST request` | DO：被傳送的內容 |

分析時區分：

- 句法形式：`NP / VP / PP / AdjP / AdvP / Clause`
- 句子功能：`S / V / O / C / OC / IO / DO`
- 語意功能：角色、用途、形式、接收者、結果等

不要把這三個層級混為一談。

## 3. 關鍵差異

指出真正造成兩個表達不同的成分。

例如：

`Send it as a POST request.`

其中：

`it`

是被傳送的東西。

而：

`as a POST request`

說明它以什麼形式被傳送。

相對地：

`Send it a POST request.`

採用：

`send + IO + DO`

因此：

`it`

變成接收者，

而：

`a POST request`

才是被傳送的東西。

比較時優先找出這種「角色變化」，而不是只比較中文翻譯。

## 4. 語意如何改變

說明句法、詞性、搭配或語序差異如何影響意思。

必要時回答：

- 誰做動作
- 動作作用在誰／什麼上
- 誰是接收者
- 哪個成分描述哪個對象
- 修飾範圍是否改變
- 替換單字後語氣是否改變

若兩個表達意思接近但語法結構不同，也應明確指出。

## 5. 是否可以互換

直接說明：

- 可以互換
- 部分情境可以互換
- 文法都成立但意思不同
- 意思接近但語氣不同
- 不可互換

不要只回答 Yes / No；簡要說明限制條件。

例如：

`fast`

與：

`quickly`

在某些副詞位置可以表達相近意思，但搭配與自然度不一定完全相同。

而：

`hard`

與：

`hardly`

通常不可互換，因為核心意思已經不同。

## 6. 使用時機與語域

只有存在實際差異時加入。

可以比較：

- 日常／正式
- 口語／書面
- 技術／一般語境
- 常見／少見
- 中性／強調
- idiomatic / unnatural

不要把「較少見」直接等同於「文法錯誤」。

Technical English 只是可能的 context，不是固定比較維度。

## 7. 最小對比例句

優先使用 minimal pairs：盡量保留相同詞彙，只改真正需要比較的部分。

例如：

`Send the data as JSON.`
→ 把資料以 JSON 格式傳送。

`Send the server the data.`
→ 把資料傳給伺服器。

對比例句的目的是隔離差異，不是增加大量新單字。

## 8. 常見誤解

只有存在實際學習風險時加入。

例如：

不要因為：

`Send it a POST request.`

與原本想表達的意思不同，就直接說這句文法錯誤。

它可以符合：

`send + IO + DO`

真正的問題是：

`it`

在這個結構中被解讀為接收者，而不是原本要傳送的內容。

## 9. 一句話記憶

只有在差異可以安全泛化時提供。

例如：

> `send + O + as + X`：O 是被傳送的內容，X 說明其形式或角色；`send + IO + DO`：IO 是接收者，DO 才是被傳送的內容。

不要把只適用於單一例句的差異包裝成通用規則。

## 比較策略

先判斷使用者比較的是哪一層：

### 單字比較

例如：

`fast` vs `quickly`

優先比較：

- 詞性
- 此處意思
- 搭配
- 語氣
- 位置
- 是否可以互換

必要時引用 `word-analysis.md` 的分析原則。

### 片語比較

例如：

`take down` vs `shut down`

優先比較：

- 整體意思
- 結構
- 搭配
- 語境
- 是否可以互換

必要時引用 `phrase-analysis.md` 的分析原則。

### 句型／文法比較

例如：

`send + O + as + X`

vs.

`send + IO + DO`

優先比較：

- 句法結構
- 成分角色
- 修飾或補足關係
- 語意如何隨角色改變

必要時引用 `pattern-analysis.md` 的分析原則。

### 完整句比較

若兩個完整句子的差異涉及主要子句、時態、語態或多層 clause，先找出真正不同的部分。

只有當局部比較不足以解釋差異時，才引用 `sentence-analysis.md` 的整句分析原則。

## 分析限制

- 比較前先判斷各表達本身是否符合英文句法，再比較意思；不要因意思不同就直接判定其中一個錯誤。
- 「文法正確」、「自然」、「常見」、「意思相同」是不同判斷維度，不可混為一談。
- 文法成立但少見，不等於文法錯誤。
- 意思相近，不代表可以在所有語境互換。
- 中文翻譯相同，不代表英文句法、語氣或搭配相同。
- 表面結構相似，不代表內部句法關係完全相同。
- 比較詞彙時限制在目前語境，不要展開大量無關 synonym。
- 比較句型時應區分句法形式、句子功能與語意功能。
- 若存在多種合理句法分析，應指出採用的分析方式，不要用有爭議的分析製造假的「A 對、B 錯」。
- 優先使用 minimal pair 隔離差異；不要用內容完全不同的兩個例句增加額外變因。
