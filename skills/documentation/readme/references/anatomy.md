# README 結構

依讀者與專案複雜度選擇區段；不是每個 README 都要有全部內容。一般順序是：標題與價值、示範或 highlights、快速開始、安裝、使用範例、設定、限制與延伸連結。

## 標題與開場

每份 README 都需要。H1 使用實際專案名稱，不加版本、口號或裝飾；其後一句以平實語言回答「做什麼」。接著用二至四句交代目標讀者、解決的問題與差異點。不要只描述實作技術，也不要讓 badge 或大圖把核心價值推到首屏之外。

## Badge 與示範

Badge 僅在提供可行動訊號時納入，例如 CI、版本、授權與 coverage；三至六個已足夠，且每個都要連到可驗證的目的地。CLI、UI、桌面程式和可視化工具通常應有示範；純函式庫以短程式範例取代。示範應呈現主要結果、具 alt text、檔案小且與目前版本一致。

## Highlights、快速開始與安裝

當專案有三項以上明確能力時，以五至八個「使用者收益」條列 highlights；避免「快速」「好用」這類無法證實的形容。快速開始必須從零到看見結果，優先控制在三至五步，先列必要前置條件，再給單一可複製的指令區塊及預期結果。完整安裝則處理其他受支援方式、版本、平台與驗證命令；依實際 manifest 決定 package manager、binary 或 source build 的優先順序。

## 使用、設定與 API

範例從最小常用案例逐步增加複雜度，使用真實 import、設定與輸出。設定表至少列 key、型別、預設值與用途，只有 schema 或原始碼能證實時才寫入。公開 API 少而小時可在 README 說明；介面大或已有生成文件時，README 只放最小範例與連結。

## 選用區段

複雜架構才加入高層資料流圖；需要外部協作才提供貢獻連結與本機測試方式；有穩定發版才連到 changelog；支援管道、限制與 non-goals 只在確實存在時說明。README 超過約 200 行時加入目錄；深入內容連到專門文件，避免入口頁成為文件站。
