# 正式 Spec 歸檔

## 解析與授權

先讀取適用的 AGENTS.md，解析專案的實際 spec workspace 與任務檔名，優先使用 owning spec；不得假設 workspace 位於程式庫內。以下 `workspace` 指解析後的根目錄。既有 `tasks.md` 與專案指定的 `task.md` 按實際檔案讀取；兩者衝突時釐清，不自行挑選。

- 只要求候選清單：唯讀，回報每項「可歸檔／不合格／待確認」、證據位置、原因與預定目的地。
- 明確要求歸檔：可執行授權範圍內已識別且合格的目標，不重複要求確認；範圍有歧義先釐清。
- 一般實作只讀目前 spec；歸檔候選查詢才可列舉指定範圍並讀狀態、必要任務、驗證摘要，按需追查驗收條件。不可預設讀入全部 archive 全文。

## 資格

只有正式 spec 的 `Status: Complete`、必要任務與驗收完成、驗證結果已記錄且無必要阻塞時，才可歸檔。日期久遠、全部勾選或單一 Complete 標記都不足以證明完成。缺少證據列待確認；Planned、InProgress、Blocked 或仍有必要待辦列不合格，不補造測試結果。

非必要後續改善若已記錄追蹤去向或不納入理由，可維持未勾選。不得為通過歸檔而將必要工作降級為可選。舊 spec 可使用既有完成證據，不強制補新欄位。

## 搬移與引用

1. 確認來源為指定 workspace 根層正式 spec，符合 `{YYYY-MM-DD-HH-mm}_{Type}-{name}`，Type 為 Feature、BugFix、Refactor、Docs、Chore。不合格式列待確認，不猜年份。排除 draft、已歸檔項目及越界路徑；解析實體路徑，拒絕指向 workspace 外部的符號連結。
2. 目的地為 `workspace/archive/{原名建立年份}/{完整原目錄名稱}/`。保留原名稱、歷史內容與 Complete 狀態，不新增 Archived 狀態。目的地存在即停止該項，不覆寫或合併。已歸檔目標再次收到請求，回報現況，不再次搬移。
3. 檢查工作區變更，保留無關修改；重疊修改無法安全區分時停止該項。先列出搬移映射與受影響引用，再執行搬移。
4. 在專案程式庫及解析後的私有 workspace 內，定位指向來源的連結與明確路徑引用，包括來源 draft、roadmap、跨 spec 與既有索引；另檢查搬移文件內的相對連結。依新位置調整，核對搬移前後是否解析到同一目標。不對歷史敘述或程式範例做無差別字串替換。
5. 已 promotion 的 draft 與已完成 spec 僅允許必要的路徑維護，不能重寫歷史決策、驗收或結果。外部 repository 或遠端引用無法更新時，明列已知影響與檢查範圍。私有規劃不可因修正引用而被複製至公開 repository。
6. 核對來源已移除、目的地檔案完整、既有有效連結仍有效、狀態及歷史保留。搬移前已破損的連結另外回報，不宣稱本次已修復。

不建立跨檔案交易引擎。部分失敗時不宣稱整批成功；回報每項實際位置、已搬移與已修正內容、剩餘問題及復原步驟。回復前先確認原位置無新資料，避免覆寫；不能安全復原就保留可辨識狀態供修復。

## 完成回報與後續工作

回報原位置、新位置、資格證據、引用調整、驗證結果及剩餘限制。不因技能更新而批次搬移既有專案。

已歸檔工作的新增需求或 bug 建立新 spec，引用歷史；同一未完成工作維持原 spec。歷史按需查閱。第一版不提供 archive CLI、不自動排程、不歸檔 draft、不強制新增索引。
